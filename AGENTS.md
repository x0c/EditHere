# EditHere

Mark on-screen UI and submit a numbered-screenshot packet to a coding assistant. Capture is per platform. Prompt assembly and named-executor dump live on the local host.

## Components

| Path | Remote | Role |
|---|---|---|
| `sdk-swift/` | `https://github.com/x0c/EditHere.git` (public); private Forgejo mirror for maintainers | iOS SDK (`EditHereCore`, `EditHere`, destinations) + sample app |
| `sdk-swift/Tools/edithere-host/` | same git as `sdk-swift/` | Shared local server: canonical prompt, package accept, fire-and-forget dump |
| `chrome/` | private Forgejo `Max/edithere-chrome` | Chrome extension capture client; POSTs packages to the host |

Android is a later capture client against the same host — not started.

## Hard constraints

- Fully decoupled from Corral. Optional adapters only.
- Shared post-mark work is the local host, not a JS (or other) SDK every platform embeds.
- One-time app entry integration; no per-control source edits required for normal use.
- Submit starts work for execution destinations; file export is for portability proof only.
- **Fire-and-forget (2026-09-13):** Submit dumps the frozen package to the named executor and assumes it finishes. Do **not** implement or expand a product task-status machine, result write-back, or result UI. Already-written plans and code for those stay dormant and **default off**. Failed or missing work is re-marked and submitted again; source edits are idempotent. Skipping this resumes wait-for-results and status chrome the user rejected as over-complicating.
- **Execution review reports (2026-09-13):** Lead with defects that make Submit look successful while the assistant never received the work (假成功). Do **not** lead with “partial / not proven / 钉死.” That framing hid the e2e bugs; the user treated the review as empty (白review / 没看懂). Do not resume task-status to “fix” fake success. Details: `sdk-swift/docs/reviews/2026-09-13-FIRE_AND_FORGET_E2E_REVIEW.md`.
- The numbered screenshots plus the generated Agent prompt are the **core product capability**. Evidence is frozen at Submit; the prompt is a derived legend. **Must read** `sdk-swift/docs/design/AGENT_PROMPT_CORE_DESIGN.md` before changing that path. The packet is only facts that locate a mark or specify the change. **Never print** packing-generation numbers, session/process lectures, or a second unannotated original. If a review finds junk in the packet, **cut it in the same turn** (user 2026-09-12: “Prompt template: 4 这是啥意思” / “全面排查废话” / “你知道元认知了就直接改”). Skipping the doc ships a weak legend, splits one batch into many sessions, or hard-codes wording into the evidence schema.
- Full visible-page annotated screenshots are required evidence.
- **An open user-visible chrome request is the session’s work.** If the user asked to change what they see on the phone, finish that (build, deliver, look at a full-device screenshot) before global instruction, attribution, or process-doc work. User correction 2026-09-12 (“正事儿没做”).
- **Do not launch Simulator to verify UI when a physical phone is available (2026-09-12).** If iPhone Max is `available (paired)`, install, test, and capture on that phone. Do **not** boot Simulator, install the sample there, or click through Simulator for screenshots. Simulator is allowed only when no physical device is online; shut it down immediately after. **Install and launch are not UI verification:** drive the same installed sample with a Debug launch argument, read the console, and capture the affected screen. Canvas-behind-popup: `-EditHereCanvasLockProbe`. Prompt preview: `-EditHerePromptPreviewProbe`. Selection-bar Close/Marks placement: `-EditHereSelectionBarProbe`. Marking hint: `-EditHereMarkingHintProbe`. The user checking the phone is final subjective acceptance, not a substitute. Skipping this delays the only device that matters, wastes time on Simulator taps, or ships a “done” the user cannot see.
- **System controls only:** if iOS already provides a standard control or presentation for the job, use it. Do **not** hand-build or custom-draw a substitute (toolbars, navigation, sheets, lists, menus, buttons, alerts, empty states, swipe-to-delete). The only allowed custom drawing is the numbered selection outline on the frozen screenshot. Details and consequences: `sdk-swift/docs/PRODUCT_KNOWLEDGE_BASE.md` § System controls. Skipping it ships fake chrome, breaks list swipe, and leaves artifacts such as a red hairline after delete.

## Verification (sdk-swift)

- Do not boot Simulator to verify annotation UI when iPhone Max is online. After a user-visible change, build a signed sample and deliver it to that phone. **Install/launch success is not UI verification:** launch the same sample with a Debug argument (`-EditHereCanvasLockProbe` / `-EditHereGeometryProbe` / `-EditHerePromptPreviewProbe` / `-EditHereSelectionBarProbe` / `-EditHereMarkingHintProbe`), read the console, capture the affected screen, and look at it before calling the work done. Simulator is allowed only when no physical device is online; shut it down after.
- After bumping `CURRENT_PROJECT_VERSION` in `Examples/EditHereSample/project.yml`, regenerate from a clean Xcode project (`rm -rf EditHereSample.xcodeproj && xcodegen generate` in that folder). An existing generated project can keep the old build number. Confirm on the built app with `plutil -extract CFBundleVersion raw …/EditHereSample.app/Info.plist`, not by reading `project.yml` alone.
- Do not treat a missed Simulator coordinate click as “the entry button does nothing.”
- Do not claim Marks swipe-to-delete accepted until consecutive deletes on device leave no leftover red fill.
- Do not claim continuous marking is silky from XCTest alone. Device feel still needs the phone capture.
- Do not install a second UI-test runner. With a phone online, prove behavior on the installed sample — do not open Simulator because package tests have no device host.
- Do not delete a working write surface or toolbar until the system replacement is on a running build.
